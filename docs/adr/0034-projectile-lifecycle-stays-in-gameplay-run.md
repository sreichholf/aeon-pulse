# Projectile lifecycle rules stay in GameplayRun

ARCH-6 ("Concentrate projectile lifecycle rules") proposed a single `ProjectileLifecycle` module to unify projectile create/retain/release/cancel/stats semantics across `ProjectilePool`, `ProjectileInstancer`, `Gameplay`, `GameplayRun`, `Scene`, and `Bullet`. The proposal framed the six files as a fork in projectile ownership. Inspection shows pooling, instanced rendering, scene interception, and motion each already have a single cohesive owner (`ProjectilePool`, `ProjectileInstancer`, `Scene`, and `Bullet` respectively per ADR 0025). The actual fork is narrower: four `this._bullets = this._bullets.filter(...)` sites in `GameplayRun.ts` (`_clearHostileBullets`, `_triggerBulletCancellation`, `_clearBulletsInRadius`, and `_tickLevelExit`'s bullet filter) plus `getBulletStatsSnapshot`. We decline to extract them.

## Decision

The four bullet-array filter sites and the stats helper stay private to `GameplayRun`. Rationale:

- **One consumer.** Every filter site and the stats helper is private to `GameplayRun`. No other module reads or mutates the live bullet array. `tickGameplay`, `checkCollisions`, and `_resolveCombat` all read `WorldState.bullets: IBullet[]` raw; the ARCH-4 pipeline invariant test asserts on `this._bullets` directly. There is no second consumer to justify a seam. A module with one consumer is a hypothetical seam, not a real one.
- **Shallow interface.** Any `BulletStore` extraction exposes 4–5 methods that mirror the four gameplay events (smart bomb → `cancelHostile`, level exit → `releaseHostile`, prop clear → `cancelHostileInRadius`, offscreen → `reap`) plus stats. The caller (`GameplayRun`) still owns the event-to-method mapping, the per-bullet effect (`CancellationPointItem` construction), and the scoring policy (`fromBomb`). The interface is nearly as complex as the implementation; the leverage at the seam is approximately zero.
- **The policy cannot travel with the code.** Cancellation scoring differs by trigger (smart-bomb cancels score 0; high-value-kill and prop-clear cancels score normally). The `fromBomb` flag, the radius, and the `CancellationPointItem` construction are gameplay decisions, not lifecycle facts. They stay in `GameplayRun` regardless of extraction, so a `BulletStore` can only ever own the `pool.destroyOrRelease(b)` call pattern — ~5 lines of dedup.
- **Predicate differences are intentional, not drift.** `_clearHostileBullets` omits the `!bullet.active` guard that `_triggerBulletCancellation` and `_clearBulletsInRadius` carry. Inspection confirms this is correct: `_clearHostileBullets` is a level-exit nuke that reaps hostile bullets regardless of in-flight cancellation state, and `ProjectilePool.release` is idempotent against double-release. The predicates differ because the semantics differ. Concentrating them either erases the intentional difference (bug) or re-exposes it as parameters (back to shallow).

This is the same shape ADR 0025 declined for motion adapters: a frozen event set with no growth pressure, where extraction relocates ~30 lines without vanishing them.

## Considered options

- **Stateful `BulletStore` that owns the `_bullets` ref.** Rejected: `_bullets` must stay as a `GameplayRun`-owned reference because `_syncWorldArrays` reassigns it from `WorldState.bullets` post-tick (ARCH-4 invariant). A stateful owner either duplicates the ref or forces a getter at every reader (`tickGameplay`, `checkCollisions`, `_resolveCombat`, the ARCH-4 pipeline test). Invasive for zero leverage.
- **Stateless helpers (pure functions, `WallInterpolator` precedent from ARCH-2).** Rejected as a poor fit: `WallInterpolator` has two consumers across two domains (gameplay collision and spawn authoring) and no injected dependency. `BulletStore` helpers would have one consumer (`GameplayRun`) and require `pool` threaded through every call. The dedup at the call site is the very thing being consolidated — argued for, but the consolidation moves ~5 lines, not a policy.
- **Closure class with pool injected at construction.** Rejected after deletion test: a class with no instance state besides the pool closure is a shell over five pure functions. The four public methods would each supply a predicate + per-bullet hook to one private `_filter`; the `pool.destroyOrRelease(b)` call collapses from 5 sites to 1 private method. That is real local consolidation but not real leverage — the caller's knowledge burden (which method on which event, what hook supplies) is unchanged.
- **Track a narrow 2-site dedup instead.** Considered: `tickGameplay`'s bullet filter (`Gameplay.ts:74`) and `_tickLevelExit`'s bullet filter (`GameplayRun.ts:687`) both reap offscreen/inactive bullets. They differ semantically (the `WorldState` version carries a `destroyOrReleaseBullet ?? b.destroy()` defensive fallback; the run-level version calls the pool directly), so the dedup is not byte-identical. Left untracked — the dedup value is smaller than the tracking overhead, and the semantic difference would have to be re-exposed as a parameter, repeating the shallowness pattern at smaller scale.

## When to revisit

Reopen this if any of these becomes true:

1. **A second consumer of the live bullet array appears.** The most plausible path is a future system that needs to read or mutate bullets outside `GameplayRun` (for example, a replay system, a bullet-time effect, or a graze detector). Then the seam becomes real and the deletion test passes.
2. **A fifth or sixth bullet-array mutation pattern emerges.** If `GameplayRun` accumulates a third cancellation variant (e.g., bullet conversion, bullet splitting, bullet time-slow), the predicate/side-effect matrix grows past what a reader can hold, and centralizing the policy earns its keep.
3. **Stats and render counts diverge in a way that bites.** Currently `getBulletStatsSnapshot` reads `this._bullets` (gameplay array) and `Scene.render` reads `_activeBullets` (render set); they legitimately differ during a frame. If a future feature needs them unified (e.g., authoritative render-unit budgeting across both surfaces), a module that owns both would clear the depth bar.
