# Finale-boss level completion is deferred out of the tick stack

A finale-boss death during the gameplay tick previously ran the full level-complete transition synchronously on `tick()`'s own call stack: the boss `onDeath` closure invoked `Game.onLevelComplete → _setState(LEVEL_COMPLETE) → _clearGameplay → run.clear()` while `_resolveCombat`, `_resolveTimedBursts`, and the other post-tickGameplay phases had not yet executed. ARCH-4 locked that tolerance with a test and a "Synchronous Run Teardown" glossary term rather than fixing it. The finale-boss `onDeath` closure now sets `hasPendingLevelComplete` on `GameplayRun` and does not call `onLevelComplete`. `Game._updatePlaying` flushes the transition after `tick()` returns on the same frame, so the run is intact for every post-tickGameplay phase. This eliminates the re-entrancy deliberately rather than tolerating it.

## Decision

- Boss `onDeath` (`GameplayRun.ts` `spawnBoss` closure) keeps its gameplay mutations synchronous — `_triggerBulletCancellation`, `score.addScore`, `score.gainLife`, and `this._boss = null` all still run inside the tick where the boss died — but replaces the `this._deps.onLevelComplete()` call with `this._hasPendingLevelComplete = true`.
- `GameplayRun` exposes `get hasPendingLevelComplete(): boolean`. `Game._updatePlaying` reads it immediately after `this._run.tick(dt)` returns, before the HUD update and before the `score.isGameOver` check. When true, `Game.onLevelComplete()` runs and `_updatePlaying` returns.
- The `onLevelComplete` dep stays in `GameplayRunDeps` because `_tickLevelExit` (the Level Exit Window completion path) still calls it synchronously. That path early-returns at the top of `tick()` and cannot re-enter the tick, so no deferral is needed or warranted.
- The unreachable `if (this._level?.isFinale)` branch of `GameplayRun.completeLevel()` is deleted. `LevelManager.update` routes finales to `spawnBoss()` and never to `completeLevel()`, so that branch was dead code; keeping it as a deferred flag-set would have implied a live in-tick caller that does not exist.
- When `hasPendingLevelComplete` and `score.isGameOver` would both be true after a tick (player on the last life, dies on the same frame the boss dies), level completion preempts game-over. The `hasPendingLevelComplete` check runs first in `_updatePlaying`. This is a deliberate rule, not an accident: the finale `gainLife()` lands synchronously in `onDeath` before the check, so the tie only arises when the player was on their absolute last life, and the chapter clear they earned by killing the boss should not be stolen by a same-frame death.

## Considered options

- **Keep the synchronous re-entrancy, rely on null/empty-safe post-tick phases.** Rejected: ARCH-4's audit showed every post-tickGameplay phase had to stay null/empty-safe forever, locked by a test that simulates the re-entrancy. That is a permanent latent hazard — one new phase that forgets the tolerance reintroduces a throw on a torn-down run. Deferring removes the hazard at the source.
- **Defer to the next frame (one-frame latency).** Rejected: the dying animation already completes before `_onDeath` fires (`BossBase._updateDying`), so the post-death world is already rendered. A one-frame delay between `tick()` returning and the level-complete screen adds latency for no correctness benefit. Flushing same-frame after `tick()` returns is off the tick call stack, which is all the re-entrancy fix requires.
- **Return a `TickOutcome` from `tick()` instead of a polled boolean.** Rejected: changes the `tick()` signature that ARCH-4 just stabilized and that every test calls as `run.tick(0.016)`. A polled boolean is the smallest contract change for a single deferred event.
- **Defer the `completeLevel()` finale branch too (consistency).** Rejected after exploration: `LevelManager` never calls `completeLevel()` for finales (the `isFinale` guard routes to `spawnBoss()`), so that branch was unreachable dead code, not a safety net. Deleting it is better than deferring it; deferral would imply a live caller that does not exist.
- **Preserve current "game-over wins" tie behavior as a zero-behavior-change refactor.** Rejected: the "game-over wins" outcome was an accident of the synchronous re-entrancy (`_setState(GAME_OVER)` clobbered `LEVEL_COMPLETE` because nothing guarded the order), not a deliberate rule. ARCH-7 rewrites this branch; freezing the accident would lock in a feel-bad finale outcome.

## Consequences

- The "Synchronous Run Teardown" glossary term is removed and replaced by "Deferred Level Completion", which names the post-fix contract. The "Bullet Active-Flag Synchronization" term is unchanged: `_triggerBulletCancellation` still runs synchronously in `onDeath`, so its in-place deactivation invariant still holds.
- ARCH-4's `Mid-Tick Teardown Tolerance` pipeline test is replaced by a `Deferred Level Completion` describe block asserting the new contract: `onDeath` does not call `onLevelComplete` synchronously, sets the flag, and all post-tickGameplay phases run on a still-alive run.
- There are exactly two `onLevelComplete` call sites in `GameplayRun` after this change: `onDeath` (deferred via flag) and `_tickLevelExit` (synchronous). The split is auditable by inspection.
- Same-tick priority (level-complete preempts game-over) is a new deliberate rule. It is effectively moot in normal play because finale `gainLife()` lands before the check, but it governs the last-life edge case and is locked by a `Game._updatePlaying` priority test.
- Rule for future in-tick level-complete triggers: any `onLevelComplete` call that originates inside `_tickWorld` (during `tickGameplay`) must defer through `hasPendingLevelComplete`. Calls that originate from `_tickLevelExit`'s own frame may stay synchronous.
